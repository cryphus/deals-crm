1. Что нужно разработать:
Небольшую CRM для работы со сделками. Данные могут редактироваться сотрудником и приходить из имитируемой внешней системы (webhook и GET API).
Стек:  Backend - PHP и Laravel; frontend - React + TypeScript; PostgreSQL, Redis, Docker Compose. Версии фреймворков на ваше усмотрение; укажите их в README.
Базовая модель сделки: id, external_id, title, status, amount, external_updated_at, external_version, created_at, updated_at. Для журнала событий и статусов фоновых операций можно использовать дополнительные таблицы.
Функциональность
- Простой список сделок и просмотр одной сделки (карточка или панель)
- Создание сделки вручную и редактирование title, status, amount
- Кнопка «Обновить из внешней CRM». Отображение состояний: «запрос принят», «обновление выполняется», «успешно обновлено», «ошибка»


Дополнительно, если останется время: поиск, фильтр по статусу и пагинация. Красивый дизайн не оценивается; достаточно простой таблицы.


Реализуйте POST /api/webhooks/deals. Это учебная сделка: она намеренно упрощена по сравнению с реальными событиями Bitrix24.
{
  "event_id": "evt_123",
  "event_time": "2026-10-15T15:30:00Z",
  "deal": {
    "id": "5678",
    "version": 18,
    "updated_at": "2026-10-15T15:29:50Z",
    "title": "Продажа курса",
    "status": "NEW",
    "amount": 49000
  }
}

В этом тесте deal.version — монотонно возрастающая версия состояния в источнике (для каждой сделки). deal.updated_at — время обновления состояния в источнике; event_time — время создания/отправки события и НЕ является версией сделки.
- Webhook быстро отвечает клиенту, а обработка выполняется через очередь Redis. Успешный HTTP-ответ о приеме возможен только после надежного сохранения события или задания, из которого обработку можно восстановить.
- Повтор одного event_id не должен повторно применять бизнес-изменение; при одновременной доставке одинаковых событий защита также должна оставаться корректной.
- Более старая версия сделки не перезаписывает более новую, независимо от порядка доставки или завершения фоновых задач.
- Входящий запрос проверяется: обязательные поля и типы, простой общий секрет в заголовке X-Webhook-Token (значение из конфигурации). Секреты нельзя помещать в Git и журналы.
- Ошибки обработки видны: можно понять, что событие получено, выполняется, применено или окончательно завершилось ошибкой.
Реализуйте GET /mock-api/deals/{id}. Успешный JSON должен возвращать те же бизнес-поля, что и webhook: id, version, updated_at, title, status, amount. Можно добавлять служебные поля по необходимости.
Предусмотрите воспроизводимые режимы:
- Успех: сразу 200 и данные сделки
- Временное ограничение: первые два запроса 429, третий запрос 200
- Постоянный сбой: каждый запрос возвращает 500
Режим можно задавать параметром/настройкой. В README опишите команды или шаги для повторения сценариев. Случайные ответы без воспроизводимого сценария не подходят.
По нажатию «Обновить из внешней CRM» поставьте фоновую задачу, прочитайте mock API, примените данные и сообщите итоговый статус. При 429/500 - ограниченные retry с возрастающей задержкой (backoff); покажите как восстановление после 429, так и финальную ошибку после исчерпания попыток.
Особая ситуация: менеджер вручную изменяет сделку, а ответ GET приходит позднее со старой версией или данными, конфликтующими с локальной правкой.
- Выберите и опишите политику «источника истины» для title, status и amount: например, внешний сервис имеет приоритет или локальные изменения сохраняются до явного разрешения конфликта.
- Последовательно реализуйте выбранное правило хотя бы для одного конфликтного сценария и покажите, что старый GET-ответ не затирает более новую внешнюю версию.
- В README укажите допущения: передаются ли локальные правки во внешнюю CRM, и как действовать при одинаковой внешней версии и разных данных.

1.6. Данные, запуск и тесты
PostgreSQL: укажите полезные индексы (например, поиск по external_id) и кратко объясните выбор.
Docker Compose: Laravel, PostgreSQL, Redis и отдельный queue worker; инструкция запуска - в README.
Тест 1: два одинаковых event_id = изменение применяется один раз.
Тест 2: более старое webhook-событие или GET-ответ не перезаписывает более новую внешнюю версию.
Тест 3: режим 429, 429, 200 приводит к успешному обновлению после ограниченных повторов.
Тест 4: постоянные 500 приводят к конечному статусу ошибки, а не бесконечной работе.
Тест 5: одно выбранное правило локального/внешнего конфликта проверяется примером или автоматическим тестом.

Первая линия назначает дату и время вводного урока; отдел подтверждения проверяет участие клиента; менеджер вводного урока (МВУ) принимает встречу и проводит урок. Нужна автоматическая передача подтвержденных встреч подходящему МВУ с учетом расписания, доступности и рейтинга.
