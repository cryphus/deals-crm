# CRM сделок — тестовое задание

Небольшая CRM на Laravel и React: ручная работа со сделками, приём webhook и фоновое обновление из имитируемой внешней CRM. Главная часть решения — надёжный приём событий, конкурентная дедупликация и защита от устаревших данных. Условия задания: [REQUIREMENTS.txt](REQUIREMENTS.txt).

Это учебный проект для локального запуска и защиты. Интеграция с настоящим Bitrix24 и модуль назначения уроков не реализуются: по второй части задания подготовлен [ответ на бизнес-кейс](docs/BUSINESS_CASE.md).

## Запуск

Нужны Git и Docker Engine / Docker Desktop с Compose v2. При первой сборке нужен доступ к Docker Hub, Packagist и npm. Для запуска приложения локальные PHP, Composer и Node не требуются.

```sh
git clone https://github.com/cryphus/deals-crm.git
cd deals-crm
```

Репозиторий закрытый; проверяющему потребуется доступ от владельца. Если исходники получены архивом, распакуйте его и откройте корневую папку проекта.

Windows PowerShell:

```powershell
./scripts/init.ps1
docker compose up -d --build --wait --wait-timeout 180
```

Linux / macOS (для генерации ключей нужен `openssl`):

```sh
sh scripts/init.sh
docker compose up -d --build --wait --wait-timeout 180
```

Скрипт создаёт игнорируемый Git файл `.env` со случайными ключами; существующий файл сохраняется. Не заменяйте его пустыми значениями из `.env.example`.

- Интерфейс: **http://localhost:5180**.
- API: **http://localhost:8180/api/deals**.
- В новой БД сделок нет. Создайте первую запись через интерфейс.
- Если порты заняты, измените `WEB_PORT` / `APP_PORT` в .env и повторите запуск. Web-клиент обращается к API через nginx, дополнительная настройка URL не нужна.
- `docker compose down` останавливает проект с сохранением данных. `docker compose down -v` удаляет его БД и Redis — это полный сброс учебного окружения.

Версии: PHP 8.4, Laravel 12.70.1, React 19.3.1, TypeScript 7.0.2, Vite 8.3.5, Node 22, PostgreSQL 17, Redis 7.4, nginx 1.28. PHP/JS-зависимости закреплены в lock-файлах.

## Демонстрационные данные

```sh
python scripts/demo.py seed
```

Команда создаёт 15 синтетических сделок с разными статусами, нулевой и дробной суммой, длинным названием. Повторный запуск сохраняет существующие записи и ваши правки. В поиске введите `Демо:`, чтобы показать только этот набор и проверить две страницы списка. Персональные данные не используются. Исходные данные: [examples/deals.json](examples/deals.json).

## Проверка сценариев

1. Создать сделку с внешним ID `5678`, названием, статусом и суммой. Изменить три бизнес-поля; сумма `0` допустима. Проверить поиск, фильтр и переход из списка в карточку.
2. Нажать **«Обновить из внешней CRM»**. Сценарий по умолчанию возвращает версию 20. Карточка показывает принятие запроса, обработку и итог; быстрая операция может завершиться между двумя опросами UI.
3. Раскрыть **«Сценарии проверки»**, выбрать **«Две ошибки 429, затем успех»**. Операция завершится успешно после третьей попытки.
4. Выбрать **«Постоянная ошибка (500)»**. После четырёх попыток будет конечная ошибка. Во время backoff операция ожидает следующей попытки; это не зависание.
5. После применения версии 20 изменить название вручную и снова запросить версию 20. Локальная правка сохранится; UI объяснит конфликт одинаковой версии. Строго большая внешняя версия заменит локальные поля.

У каждой новой sync-операции отдельный счётчик mock-сценария. Повторное нажатие после завершения запускает новую операцию. Проверка всех пяти обязательных технических сценариев автоматизирована:

```sh
python scripts/smoke.py
```

Нужен Python 3.10+ (`python3` вместо `python` на некоторых системах). Smoke работает с настоящими HTTP, PostgreSQL, Redis и worker; создаёт уникальные синтетические записи и не удаляет существующие данные. Он проверяет повторные доставки webhook, старый webhook/GET, восстановление после 429, конечную ошибку после 500 и выбранную политику конфликта. Настоящую конкурентность отдельных SQL-сессий дополнительно проверяет `backend/tests/concurrency.php`.

## Как устроено решение

```text
React → nginx → Laravel API → PostgreSQL: operations (durable inbox)
                                    ↓ dispatcher каждые 2 секунды
                                  Redis → worker → mock HTTP
                                              ↓
                                  lock + проверка версии → deals
```

Webhook получает `202` только после сохранения события в PostgreSQL. Уникальный индекс event_id защищает от конкурентных дублей. API при приёме не обращается к Redis; отдельный dispatcher публикует задания и восстанавливает потерянные публикации и просроченные аренды worker. Бизнес-изменение и успешный статус операции фиксируются одной SQL-транзакцией. Fencing token не даёт старому worker завершить уже перехваченную операцию.

Для одной сделки используются транзакционная advisory-блокировка PostgreSQL и блокировка строки. Ответ внешнего GET читается до транзакции, но его версия сравнивается внутри блокировки после ответа. Поэтому поздний GET v18 не затирает уже применённый webhook v19. Доставка задач допускает повторы; повторного бизнес-применения одного события не происходит.

При 429, 500 и сетевых ошибках — максимум **4 попытки**, задержки **2, 5, 10 секунд** плюс время очереди, HTTP и опроса dispatcher. Невалидный ответ источника завершается ошибкой без повторов. Состояния операции: `received`, `processing`, `succeeded`, `failed`; API возвращает число попыток, последнюю ошибку и результат применения.

Подробности, схема API, webhook-пример и обоснование индексов: [ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Политика данных и допущения

| Ситуация | Поведение |
| --- | --- |
| Внешняя версия больше сохранённой | Внешняя CRM заменяет title, status, amount |
| Версия меньше сохранённой | Данные игнорируются: ignored_stale |
| Одинаковая версия, одинаковые поля | Повтор не применяется: ignored_equal_version |
| Одинаковая версия, разные поля | Локальные поля сохраняются: ignored_equal_version_conflict |
| Ручная правка | Не меняет внешнюю версию и не отправляется во внешнюю CRM |
| Повторный event_id с другим телом | Используется первое надёжно принятое тело |

Порядок определяет только deal.version, а не event_time, время источника или порядок выполнения задач. Новая внешняя версия сознательно имеет приоритет над локальной правкой. Для ручной сделки без внешнего ID создаётся manual-UUID; учебный mock обслуживает любой такой ID. Реальная интеграция потребовала бы явного связывания записей.

## Проверки кода

Команды выполняются из корня запущенного проекта:

```sh
docker compose exec -T api composer lint
docker compose exec -T api composer validate --strict
docker compose exec -T api composer audit --locked
docker compose exec -T db createdb -U crm crm_test
docker compose exec -T -e DB_DATABASE=crm_test -e DB_URL= -e APP_ENV=testing api php artisan test
docker compose exec -T -e DB_DATABASE=crm_test -e DB_URL= -e APP_ENV=testing api php tests/concurrency.php
python scripts/smoke.py
```

createdb нужен один раз; сообщение already exists при повторе не мешает тестам. PHPUnit использует RefreshDatabase **только в отдельной PostgreSQL БД crm_test**. Bootstrap проверяет эффективную конфигурацию, включая URL и read/write overrides, до подключения. Не отключайте эту защиту и не передавайте рабочую БД.

Frontend проверяется на хосте с Node >=22.12:

```sh
cd frontend
npm ci
npm run lint
npm run typecheck
npm run build
npx playwright install chromium
npm run test:regression
npm audit --audit-level=high
```

Многопроцессный PHP regression создаёт независимые PostgreSQL-сессии и одновременно доставляет дубли/разные версии отсутствующей сделки. Он работает только с `crm_test` и удаляет только собственные уникальные fixtures. Browser regression проверяет CRUD, поиск, фильтры, пагинацию, гонки GET/PATCH, ошибки чтения карточки и адаптивность списка с подменённым API; к рабочей БД он не обращается. GitHub Actions повторяет проверки и сканирует Git-историю на секреты. Правила оформления: [CONTRIBUTING.md](CONTRIBUTING.md).

## Границы учебного решения

Авторизации сотрудников нет; порты опубликованы только на 127.0.0.1, PostgreSQL и Redis не опубликованы. PHP запускается через artisan serve; это конфигурация для локальной защиты. operations хранит события и текущие состояния, но не историю каждого перехода. Поиск ILIKE рассчитан на небольшой набор данных. Отдельный mock и recovery dispatcher нужны для воспроизводимой асинхронной демонстрации.

Для production добавил бы авторизацию и роли, HTTPS и ротацию webhook-секрета, лимиты запросов, аудит ручных правок и попыток, метрики/алерты, reconciliation, retention с окном дедупликации, резервное копирование с проверкой восстановления, закрытый mock и PHP-FPM, минимальные права контейнеров/БД, закрепление образов по digest, нагрузочные и crash-тесты. Также понадобятся decimal-safe money на всём пути, интерфейс разрешения конфликтов и реальные правила связывания внешних ID.

## Инструменты и время

Использован Codex для проектирования, написания backend/frontend, тестов, бизнес-кейса, документации и проверки кода. ИИ участвовал в разработке и ревью; это раскрывается согласно ТЗ. Для разработки и проверки применены Laravel/Pint, React/TypeScript, Biome, Playwright, Composer/npm и Docker.

Ориентировочно **2,5–3 часа активной работы** с параллельным использованием ИИ. Точный поминутный учёт не вёлся; оценка включает разработку, итерации интерфейса, тестирование, исправления и документацию, исключает ожидание и перерывы. Это приблизительная реконструкция, а не сумма времени всех параллельных исполнителей.
